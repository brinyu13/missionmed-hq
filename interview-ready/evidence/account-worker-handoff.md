## Same-connection fence and restoration

The live owner's read-only `wp-includes/class-wpdb.php` query/check_connection branch was inspected through the exact permitted SSH path. It retries failed writes after reconnecting; a pre-write lock check alone would be insufficient. Foreman expressly admitted a narrow request-scoped subclass for this case.

`MMed_IR_Locked_DB` copies the original wpdb's visible/public/protected properties in child-class scope, reuses exactly the original mysqli handle and never runs its parent constructor. Private core properties retain defaults; actual native-driver compatibility remains a live-release gate. It disables query error display only on this temporary object. `db_connect()` and `check_connection()` always return false. Before every metadata SQL query it confirms the original handle, server connection ID and IS_USED_LOCK owner. An inherited failed query cannot reconnect or retry a write. The original global wpdb object and its properties are not mutated by this wrapper and are restored in finally; RELEASE_LOCK uses only the original handle, with no reconnect. Native calls fall back to actual mysqli in production. Only the test file defines namespaced fixture functions.

A response can be lost after a committed canonical write. That is an ambiguous acknowledgement, handled by identical-command retry; it is not a claim that networking can undo an already committed write. A disconnected connection releases its advisory lock at the server; finally cannot forcibly release a dead handle, and never creates a replacement connection.
