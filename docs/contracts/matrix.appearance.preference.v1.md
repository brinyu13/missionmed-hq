## Necessity decision and actual precedent

Current live MMED_Dashboard_Experience::save_preference() calls update_user_meta(get_current_user_id(), its private key, enum), then reads the preference. Verified live source SHA63e9c2f8aa69681ae271c6630643df6fa2d791a07dd7c9a315561cdb14595e89 on2026-10-14. Reuse the native storage primitive with isolated key and explicit failure handling; do not copy its ignored-write-result behavior or repurpose classic/matrix2 semantics.
Appearance is one low-impact intent enum, with no document edit, payment, entitlement or irreversible state. Strong monotonic revisions/CAS and a new named-lock/reconnect prerequisite are unnecessary for the approved outcome. Choose native replace semantics and honest observed readback, with per-tab serialized saves. No total order between tabs/devices, stale-revision rejection or exactly-one-physical-row promise. This is an explicit revision of an unratified proposal, not weakening a published/accepted interface.
WordPress can add duplicate rows during concurrent first writes; update_user_meta without prev_value updates all existing rows for the same subject/key. Rather than invent uniqueness, inspect all values natively, accept homogeneous valid rows as one logical choice, report conflicting rows as ambiguous, and let a later deliberate self save overwrite only this key's rows. No deletion or background repair. WordPress internal reconnect does not need a new suppression mechanism because this contract owns no DB lock or CAS invariant; uncertain outcomes still cannot claim persistence.
Primary source semantics: https://developer.wordpress.org/reference/functions/update_user_meta/ and https://developer.wordpress.org/reference/functions/update_metadata/. These support the primitive; they do not establish new API behavior on production.

## Exact storage and read contract

One logical key _mmed_matrix_appearance_v1 in existing current-subject WordPress user-meta. Persist only scalar string dark | light | auto through native update_user_meta(current_user_id,key,mode), with NO prev_value. Schema version1 is encoded in key and API contract. No additional revision row/option/table/DB/service/identity system. No custom raw SQL, GET_LOCK, DB wrapper, profile save, other meta key, account/access/entitlement change or app-owned preference write.
Native read: invalidate only current subject's user_meta object-cache entry, then get_user_meta(subject,key,false), checking native storage error immediately without logging its content. Do not return/cache other keys/rows or account data. No custom PHP object deserialization; validate returned values as scalar exact enum. Do not fetch raw user exports or add a broad account bootstrap.
Safe snapshot exactly {contract:"matrix.appearance.preference.v1",version:1,mode,revision,auto_policy:"os-browser",state}. revision is an informational content label, NEVER monotonic/CAS/If-Match: v1:dark, v1:light, v1:auto, v1:absent, v1:invalid or v1:ambiguous. Re-selecting a prior mode may repeat its revision. Clients must not infer request order, uniqueness, time or ABA detection from it.
States: no rows -> absent,dark,v1:absent; one or multiple homogeneous exact enums -> valid,that mode,v1:mode; multiple different but valid enums -> ambiguous,dark,v1:ambiguous; malformed/unknown row -> invalid,dark,v1:invalid. Native DB/cache-read failure ->503, never classify as absent or success. Empty/invalid values are not silently repaired. Ambiguous is a concurrency outcome, not an identity problem; a later deliberate own-mode save may converge these valid rows. Invalid storage rejects writes pending separately authorized recovery.

## Write, conflict and failure semantics

Validate session/CSRF/body and read current key. Invalid record ->409 without write. Absent/valid/ambiguous allows exactly one native update_user_meta(subject,key,mode) call. It may add a row or replace all existing rows for this key; it never touches another subject/key. Read all values again after current-subject cache invalidation. Do not add transactions/lock/retry loops.
No conditional update/CAS: another tab/device can overwrite a successful save. Policy is native replace by successful applied update for existing rows; no global request/response/commit ordering promise. First-write conflicts may leave heterogeneous duplicate rows, which are reported unconfirmed rather than inventing a winner.
Write-response branch precedence is exact: (1) any captured write error or readback error/unavailability ->503 mmed_appearance_unavailable regardless of matching values; (2) invalid stored readback ->409 mmed_appearance_invalid_record; (3) valid different/ambiguous observed readback ->409 mmed_appearance_superseded with safe snapshot; (4) absent/nonconforming result after save ->503 unconfirmed; (5) clean valid matching readback ->200, with native false classified already-selected/no new mutation and positive native return classified observed matching save. A positive return alone is NOT persistence acceptance; absent dark default is never matching persisted readback. Caller adopts current valid409 snapshot or dark ambiguous/invalid fallback and requires another deliberate choice. No saved toast on503/409 or blind retry. Capture write-error presence immediately before readback can clear it. Never render raw DB error or claim rollback of an uncertain save; authenticated GET reconciles actual current state.
Stable handler errors {code,message,data:{status,snapshot?}}: mmed_appearance_invalid_request400, mmed_appearance_auth_required401, mmed_appearance_csrf_denied403, mmed_appearance_invalid_record409, mmed_appearance_superseded409, mmed_appearance_unavailable503. Snapshot only on409, using safe contract. Earlier WP authentication-layer native401/403 errors remain recognized by status.
Client: exactly one in-flight save per tab, disable choices while saving, no auto retry/debounce writes or pending second submission. Apply only this tab's current request result; ignore obsolete in-memory read responses using a local generation counter, which is never persisted or confused with server revision. On timeout/error retain last acknowledged usable appearance with explicit unconfirmed status, then perform read-only reconciliation; network success alone never means saved. Refresh on reload/foreground/restoration and after conflict. If another tab/device changes the preference later, the next refresh may adopt it; no realtime guarantee or inter-tab/channel/global sync service.
