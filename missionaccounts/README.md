# MissionAccounts

Isolated production candidate for `MX-MISSIONACCOUNTS-5301P`.

This directory intentionally does not modify protected Matrix runtime assets. The Matrix route, Kinsta gateway, production database migration, and provider activation remain feature-off until the Matrix runtime lock and mission registration gates pass.

## Local verification

```bash
npm --prefix missionaccounts test
npm --prefix missionaccounts run test:postgres
npm --prefix missionaccounts run test:historical-import
npm --prefix missionaccounts run build:canon
PORT=4179 MISSIONACCOUNTS_AUTH_MODE=local npm --prefix missionaccounts run dev
```

The PostgreSQL checks apply every migration, in order, to temporary local-only PostgreSQL clusters. The primary check exercises billing, attendance correction, exam, comp, Stripe payment setup, automatic-billing consent, the bounded 24–48-hour automatic-charge dispatcher, hosted invoicing, Zoom reconciliation, one-charge-per-attendance-day, and notification-outbox transactions. The historical check verifies the exact 5000B ledger, identity graph, source-manifest, and Zoom export hashes before building private mode-0600 SQL and manifest artifacts; imports all preserved source and reconciliation rows; proves an exact replay is a no-op; runs the production post-import checks; and proves that no billing decision, invoice, charge, verified $300 ceiling, Matrix identity, enabled feature flag, or production mutation is created. The canon build verifies the Founder-approved 5300A SHA-256 before materializing the browser artifact. Generated HTML and private import artifacts are intentionally gitignored because they contain or bind real historical data. Local auth is development-only and fails closed in production.

The isolated `Dockerfile` packages only the server, the scrubbed production shell, and its two browser runtime modules. It cannot copy `public/index.html`, `public/canon-manifest.json`, historical imports, local environment files, or other private build inputs. `railway.json` is scoped to this directory and does not change the repository-root MissionMed HQ service definition. A production process also refuses to start until both database target variables are present.

To build an authorized private import bundle without applying it, provide an absolute output path:

```bash
npm --prefix missionaccounts run build:historical-import -- --output /absolute/private/path/historical-import.private.sql
```

The companion manifest is written to `historical-import.private.sql.manifest.json` unless `--manifest` supplies another private path. Authorized production operators use `npm run migrate:production` followed by `npm run import:historical:production`; both commands require an exact isolated Supabase project-ref/hostname binding and an explicit ticket-scoped approval token. See `docs/PRODUCTION_ACTIVATION_PACKET.md`.

All production capabilities default off. `MISSIONACCOUNTS_STUDENT_CONTACTS=1`, `MISSIONACCOUNTS_BILLING_DECISIONS=1`, `MISSIONACCOUNTS_ATTENDANCE_CORRECTIONS=1`, `MISSIONACCOUNTS_EXAM_PLANS=1`, `MISSIONACCOUNTS_COMP_DAYS=1`, `MISSIONACCOUNTS_PAYMENT_METHOD_SETUP=1`, `MISSIONACCOUNTS_AUTO_BILLING=1`, `MISSIONACCOUNTS_HOSTED_INVOICES=1`, `MISSIONACCOUNTS_NOTIFICATIONS=1`, and `MISSIONACCOUNTS_ZOOM_SYNC=1` are effective only on a configured runtime. Every browser mutation requires an `Idempotency-Key` header. Stripe API version override is optional and must come from a verified account readback through `MISSIONACCOUNTS_STRIPE_API_VERSION`; otherwise Stripe uses the account default.

The internal charge worker is `POST /api/internal/charges/drain`, authenticated with `MISSIONACCOUNTS_WORKER_TOKEN`. It asserts configured Stripe Test Mode before claiming database work, accepts batches of 1–25, dispatches only verified and fully approved billable days from 24 through 48 hours after attendance computation, and records older eligible days as review exceptions instead of charging them. A provider submission failure creates student/admin notices and is never automatically retried; stale claims alone may be reclaimed after ten minutes with the same Stripe idempotency key. No recurring scheduler or production endpoint invocation is configured by this repository. Notification delivery requires the same separate worker token plus an explicitly configured HTTPS transport; absent those, the notification worker fails closed before claiming any outbox row.

The Zoom provider port is `POST /api/internal/zoom/sync`, also worker-token authenticated and independently gated by `MISSIONACCOUNTS_ZOOM_SYNC=1`. The default provider is deliberately disconnected. A concrete least-privilege Server-to-Server OAuth client is included, but it is constructed only when `MISSIONACCOUNTS_ZOOM_MODE=configured` and all of `MISSIONACCOUNTS_ZOOM_ACCOUNT_ID`, `MISSIONACCOUNTS_ZOOM_CLIENT_ID`, `MISSIONACCOUNTS_ZOOM_CLIENT_SECRET`, `MISSIONACCOUNTS_ZOOM_HOST_USER_ID`, and `MISSIONACCOUNTS_ZOOM_MEETING_RULES_JSON` are present. The rules value is an explicit JSON allowlist such as `[{"meeting_id":"12345678901","step":"s1"},{"meeting_id":"10987654321","step":"s23"}]`; there is no topic or time heuristic that could import unrelated meetings. The OAuth app must grant both granular meeting-report scopes `report:read:user:admin` and `report:read:list_meeting_participants:admin` (the client also accepts the legacy `report:read:admin`). Tokens are cached only in process memory, Zoom-provided API origins are restricted to HTTPS `zoom.us`, report and participant pages are exhausted, recurring UUIDs are encoded according to Zoom's requirements, and only meetings that fall inside a persisted MissionAccounts billing cycle are accepted. Confirmed sessions reconcile only through exact existing identities; unknown attendees become isolated review records and are never silently merged. Successful runs persist immutable evidence, attendance events, recomputed one-per-calendar-day billing facts, and operational health while creating zero automatic identity decisions, billing approvals, invoices, or charges. Failed configured-provider runs persist a failed sync and one review exception without changing attendance or billing. No Zoom credential or production schedule is committed or inferred.

The container also includes `npm run worker:zoom-sync`, a scheduler-safe one-shot command. It submits exactly the previous complete `America/New_York` calendar day, including daylight-saving boundaries, with a stable day idempotency key. It requires `MISSIONACCOUNTS_INTERNAL_BASE_URL` and the private `MISSIONACCOUNTS_WORKER_TOKEN`, refuses non-HTTPS remote origins, emits aggregate controls only, and never receives Zoom credentials itself. Registering its daily schedule and worker identity remains an explicit provider activation step.

Stripe supports three independent default-off workflows. Payment-method setup saves a reusable Stripe method without authorizing automatic billing. Automatic billing requires separate versioned consent and uses a bounded 24–48-hour $25-per-billable-day worker. Hosted invoicing creates a real Stripe `send_invoice` object, adds the approved line item, finalizes and sends it, persists only safe provider references and URLs, and reconciles Sent, Paid, Overdue, Voided, and Failed through signed webhooks. Live setup or other mutations additionally require `MISSIONACCOUNTS_STRIPE_MODE=live`, a matching Live restricted key, `MISSIONACCOUNTS_STRIPE_LIVE_MUTATIONS=1`, and the exact workflow flag; Test success cannot cross that boundary. Exact provider gates are in `docs/PROVIDER_ACTIVATION_PACKET.md`.
