Part 0: Self-Reconciliation

Before building anything new, I must reconcile what MR-1364 concluded, what holds up, what was wrong, and what was incomplete.

What MR-1364 Concluded

The MR-1364 audit reached five core conclusions:

  1. The protocol system is conceptually sound but overengineered in practice. The three-file architecture (PRIMER + MASTER_KNOWLEDGE + KNOWLEDGE_INDEX) has correct role separation but has grown past the point where loading all three is efficient. Universal P0 load consumes 20-32% of context window before any work begins.
  2. The MR-00144 failure proved the orchestration layer cannot plan without reading code. Three of seven proposed STAT threads would have duplicated existing work because the planning session relied on stale knowledge files instead of actual source files.
  3. Compliance degrades on secondary rules. Pre-flight checks hit ~95% compliance. Screenshot protocol hits ~20%. The more rules in the PRIMER, the less reliably any individual rule is followed.
  4. The 3-layer AI model (ChatGPT/Claude/Codex) should become 2-layer (Claude/Codex). The translation overhead between ChatGPT (planning) and Codex (implementation) loses context. Claude can plan AND read code in the same session.
  5. Knowledge files are snapshots that go stale. MASTER_KNOWLEDGE was compiled once and not systematically updated. The canonical architecture document contradicted the actual code (Supabase auth usage). Code is truth; documents are claims about truth.

Detailed Flow for Each Task Type

1. Planning Flow

TRIGGER: "I need to plan [feature/system/project]" STEP 1: Claude reads PRIMER_CORE + KNOWLEDGE_INDEX STEP 2: Claude reads ALL relevant source files (actual code, not summaries) STEP 3: Claude reads last 10 learnings STEP 4: Claude produces plan WITH file-level evidence STEP 5: Plan includes "Current State" section citing actual files read STEP 6: Plan includes Codex Implementation Brief (if code changes needed) OUTPUT: Plan document with evidence + Codex brief NEXT: Dr. Brian reviews. If approved, Codex executes brief.

2. Implementation Flow (Code)

TRIGGER: "Build [feature]" or approved plan from Step 1 STEP 1: Claude produces Implementation Brief: - Exact files to create/modify - Exact changes per file - Validation criteria - What NOT to touch STEP 2: Codex executes the brief STEP 3: Codex produces execution report STEP 4: Claude reviews Codex output against the brief STEP 5: If issues found: Claude produces fix brief, Codex re-executes OUTPUT: Working code + execution report NEXT: Dr. Brian reviews. Deploy if approved.

3. Debugging Flow

TRIGGER: "This is broken: [description]" STEP 1: Claude reads the broken file(s) + error logs STEP 2: Claude diagnoses root cause with evidence (line numbers, state) STEP 3: Claude produces fix brief for Codex - OR fixes directly if change is small (< 20 lines) STEP 4: If Codex used: Codex applies fix, Claude validates STEP 5: If direct fix: Claude applies, verifies, reports OUTPUT: Fixed code + root cause analysis NEXT: Close.

4. Audit Flow

TRIGGER: "Audit [system/page/code]" STEP 1: Claude reads PRIMER_CORE + KNOWLEDGE_INDEX STEP 2: Claude reads ALL actual source files for the audit target STEP 3: Claude produces audit report with evidence from real files - Every finding must cite file + line number or section - No findings based on assumed state STEP 4: Report includes prioritized action items OUTPUT: Audit report (HTML or DOCX) NEXT: Dr. Brian reviews. Action items become planning tasks.

5. Deployment Flow

TRIGGER: "Deploy [system/change]" STEP 1: Claude runs HTML Deployment Lock checklist (if HTML app) STEP 2: Claude produces deployment checklist: - Pre-deployment state capture - Backup creation - Version header update - Exact deployment steps - Post-deployment validation steps STEP 3: Codex executes checklist STEP 4: Claude validates post-deployment state OUTPUT: Deployed system + validation report NEXT: Close.
Operating Principle: Claude thinks. Codex builds. Claude verifies. ChatGPT advises (only when asked). No AI operates without reading real files first.

2. Task Progression System

How Tasks Move Forward

Every task follows the same lifecycle. The state transitions are deterministic, not judgment-based.

NOT STARTED | v (Prompt executed) IN PROGRESS | +--> BLOCKED (dependency missing or error encountered) | | | v (Blocker resolved) | IN PROGRESS | v (Work complete, output produced) REVIEW | +--> IN PROGRESS (issues found during review) | v (Review passed) COMPLETE

Completion Validation

A task transitions from REVIEW to COMPLETE only when ALL of these are true:

  1. Output exists (file created, code deployed, document produced)
  2. Output matches the task's acceptance criteria
  3. No regressions introduced (for code tasks: existing systems still work)
  4. Execution report written (scaled by risk level)
  5. Learning appended
  6. Activity log entry written

How Next Step is Determined

The executing AI MUST include a NEXT ACTION block at the end of every response. This block tells Dr. Brian exactly what to do next. No ambiguity. No "you could do X or Y." One clear next action with the exact prompt to run.

3. Human-Readable Dashboard Format

Every AI response that completes a task or reports progress MUST end with this standardized block. This is not optional. This is the control interface.

======================================== CURRENT STATE ======================================== Phase: [PLAN / BUILD / AUDIT / FIX / DEPLOY / STRATEGY] Task: [What is being done right now] Status: [NOT STARTED / IN PROGRESS / BLOCKED / REVIEW / COMPLETE] LAST ACTION ======================================== What was done: [1-2 sentence summary] Output: [File path or deliverable reference] NEXT ACTION ======================================== What to do: [Clear, specific next step] Which AI: [CLAUDE / CODEX] Prompt to run: [Exact prompt text, copy-paste ready] ========================================
The "Prompt to run" field is the key innovation. Dr. Brian should never have to figure out what to type next. The system tells him. He copies the prompt, pastes it into the correct AI, and the work continues. Zero cognitive overhead for determining the next step.

Deprecation Markers

Deprecated files get a header block that AI systems will recognize and respect:

# DEPRECATED # This file has been replaced by: [new file path] # Do NOT load this file. Load the replacement instead. # If a prompt references this file, redirect to: [new file path] # Deprecation date: [date] # Authority: MR-1367

This marker must be the first content in the file, before any other text. AI systems parsing the file will see this immediately and redirect.

Context Window Guardrails

To prevent the system from drifting back toward context overload:

  1. PRIMER_CORE must stay under 150 lines. If a new rule needs to be added, an existing rule must be moved to an extension or removed. This is a hard cap.
  2. No file in _KNOWLEDGE/ may exceed 300 lines. If it grows past 300, it must be split further.
  3. P0 universal load must stay at exactly 2 files. Any proposal to add a third P0 file must include a justification and a measurement of the token cost.
  4. Extensions are loaded, not linked. An extension file that says "also load X" creates a chain loading problem. Extensions must be self-contained.

Part 6: Claude / Codex Collaboration Model

The exact rules for how Claude and Codex work together, designed specifically to prevent the MR-00144 failure mode: planning without reading code.

The MR-00144 Rule (Non-Negotiable): No AI may produce a plan, architecture decision, or implementation recommendation about a system without first reading the actual source files for that system. Knowledge files are claims about reality. Source code is reality. When they conflict, code wins.

When Claude Must Read Code Before Planning

Claude MUST read actual source files (not knowledge summaries) before producing output when:

  1. The task involves modifying an existing system. Read the file being modified. Read its immediate dependencies. Cite line numbers in the plan.
  2. The task involves building something that might already exist. Search for it first. The MR-00144 audit found 3 of 7 threads proposing to build systems that already existed.
  3. The task involves architecture decisions about a system. Read the actual implementation, not the architecture document. If the architecture document says "Supabase is not used for auth" but the code calls supabaseClient.auth.setSession(), the code is correct.
  4. The task references a "canonical document" or "architecture spec." Read both the document AND the code it describes. Report discrepancies.

When Codex Must Validate Against Real Files

Codex MUST validate its work against the actual filesystem when:

  1. Creating a new file. Before creating, check if a file with the same name or purpose already exists in the target directory.
  2. Modifying existing code. Read the current version of the file before making changes. Do not apply changes to a stale cached version.
  3. Following an implementation brief. Before executing, verify that the files referenced in the brief actually exist at the paths specified. If a path is wrong, report it instead of guessing.
  4. After completing work. Read the output file to verify the changes were applied correctly. Run any available tests or validation scripts.

When Claude Must Review Codex Work

Claude reviews Codex output when:

  1. The task is HIGH risk. Any production code change, deployment, or system architecture modification must be reviewed by Claude before being considered complete.
  2. The implementation brief was complex. If the brief had more than 3 files or involved cross-system changes, Claude reviews the output for consistency.
  3. Codex reported issues during execution. If Codex flagged blockers, unexpected state, or deviations from the brief, Claude investigates before proceeding.

Claude review means: read the actual output files, compare against the implementation brief, verify no regressions, and produce a review summary.

Preventing Planning Drift from Real State

The following rules prevent the scenario where plans diverge from what actually exists in the codebase:

Rule 1: Evidence Requirement

Every claim about current system state in a plan must include a file path and reference. "The boot function is incomplete" must cite the file and line where the boot function exists. If you cannot cite a file, you have not verified the claim.

Rule 2: Staleness Declaration

If a plan references a knowledge file (MASTER_KNOWLEDGE, system context, architecture doc), it must include a staleness disclaimer: "This information is from [file], last updated [date]. It may not reflect current code state." Then verify the critical claims against actual code.

Rule 3: Build-Exists Check

Before any plan proposes building a new component, the planner must search for existing implementations. Search method: grep the codebase for function names, class names, or feature keywords that match the proposed component. If found, switch from "build" to "audit/extend."

Rule 4: Handoff Fidelity

When Claude hands off to Codex, the implementation brief must include a "Current File State" section that lists every file Codex will touch along with the date/time Claude last read it. This prevents Codex from working with a stale picture of the codebase.
